# Спецификация фронтенда: подключение и работа с БД мини-CRM

## 1. Технологии и общие принципы

- React.
- TypeScript.
- Supabase JavaScript Client (`@supabase/supabase-js`).
- Supabase Auth — авторизация пользователей.
- PostgreSQL — хранение данных и выполнение бизнес-правил.
- Supabase Row Level Security (RLS) — разграничение доступа к данным.

### Основные принципы

1. Фронтенд взаимодействует с БД только через Supabase Client.
2. Все ограничения доступа должны обеспечиваться PostgreSQL и RLS, а не только проверками на клиенте.
3. Фронтенд не должен самостоятельно реализовывать правила переходов между статусами — их проверяет БД.
4. Изменение статуса задачи выполняется исключительно через RPC-функцию `change_task_status`.
5. История изменений доступна только для чтения. Её формирование выполняется на стороне БД.
6. Service Role Key запрещено использовать во фронтенде.

## 2. Подключение к Supabase

### 2.1. Переменные окружения

В корне проекта создать `.env.local`:

```env
VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=
```

Значения получить в настройках Supabase-проекта.

Файл `.env.local` не должен попадать в Git. В репозитории необходимо предусмотреть `.env.example` с названиями переменных без секретных значений.

### 2.2. Инициализация клиента

Создать модуль `src/shared/api/supabase.ts`.

```ts
import { createClient } from '@supabase/supabase-js';

const supabaseUrl = import.meta.env.VITE_SUPABASE_URL;
const supabaseAnonKey = import.meta.env.VITE_SUPABASE_ANON_KEY;

if (!supabaseUrl || !supabaseAnonKey) {
  throw new Error('Supabase environment variables are missing');
}

export const supabase = createClient(
  supabaseUrl,
  supabaseAnonKey
);
```

Использовать один экземпляр клиента во всём приложении.

## 3. Авторизация и профиль пользователя

### 3.1. Авторизация

Использовать Supabase Auth.

Доступные операции:
- авторизация по email и паролю;
- выход из системы;
- получение текущей сессии;
- восстановление сессии после перезагрузки страницы.

Методы Supabase:
- `supabase.auth.signInWithPassword()`;
- `supabase.auth.signOut()`;
- `supabase.auth.getSession()`;
- `supabase.auth.onAuthStateChange()`.

Публичная регистрация пользователей отключена. Создание пользователей выполняется вручную через Supabase Auth.

### 3.2. Получение профиля

После авторизации получить профиль пользователя из `public.profiles`.

Структура:

| Поле | Тип | Описание |
|---|---|---|
| id | UUID | Совпадает с `auth.users.id` |
| role | TEXT | `manager` или `executor` |

Запрос:

```ts
const { data, error } = await supabase
  .from('profiles')
  .select('id, role')
  .single();
```

Идентификатор пользователя получать из текущей Auth-сессии, а не хранить отдельно как источник истины.

### 3.3. Управление состоянием авторизации

Предусмотреть состояние авторизации приложения:

- загрузка сессии;
- пользователь не авторизован;
- пользователь авторизован;
- профиль загружается;
- профиль успешно загружен;
- ошибка получения профиля.

Роль пользователя использовать для отображения соответствующего интерфейса.

Важно: проверка роли на фронтенде нужна для интерфейса, но не является механизмом безопасности. Реальный доступ контролируется RLS.

## 4. Модель данных

### 4.1. profiles

Профили пользователей и их роли.

| Поле | Тип |
|---|---|
| id | UUID |
| role | TEXT |

### 4.2. objects

Объекты, к которым привязаны задачи.

| Поле | Тип |
|---|---|
| id | UUID |
| name | TEXT |
| address | TEXT |

### 4.3. tasks

Задачи.

| Поле | Тип |
|---|---|
| id | UUID |
| title | TEXT |
| description | TEXT, nullable |
| object_id | UUID |
| assignee_id | UUID |
| status | TEXT |
| author_id | UUID |
| created_at | TIMESTAMPTZ |

Допустимые статусы:

- `new` — новая;
- `in_progress` — в работе;
- `review` — на проверке;
- `accepted` — принята;
- `revision` — на доработке.

### 4.4. task_status_history

История изменения статусов задач.

| Поле | Тип |
|---|---|
| id | UUID |
| task_id | UUID |
| changed_by | UUID |
| from_status | TEXT, nullable |
| to_status | TEXT |
| comment | TEXT, nullable |
| created_at | TIMESTAMPTZ |

История создаётся автоматически триггерами БД:
- при создании задачи;
- при изменении её статуса.

Фронтенд не должен самостоятельно добавлять записи в эту таблицу.

## 5. Разграничение доступа

Доступ определяется ролью пользователя и политиками RLS.

### 5.1. Менеджер (`manager`)

- Получает все профили пользователей.
- Получает все объекты.
- Получает все задачи.
- Получает всю историю изменений.
- Может создавать, редактировать и удалять объекты.
- Может создавать, редактировать и удалять задачи.
- Может менять исполнителя задачи.
- Может принимать задачу или возвращать её на доработку.

### 5.2. Исполнитель (`executor`)

- Получает только собственный профиль.
- Получает только объекты, к которым привязаны назначенные ему задачи.
- Получает только назначенные ему задачи.
- Получает историю только своих задач.
- Может менять статус назначенной ему задачи в рамках разрешённых переходов.
- Не может изменять остальные поля задачи.

Фронтенд должен выполнять обычные запросы без самостоятельной фильтрации чужих данных в качестве механизма защиты. RLS ограничивает доступ на стороне БД.

## 6. Работа с объектами

### 6.1. Получение списка

Таблица: `public.objects`.

```ts
const { data, error } = await supabase
  .from('objects')
  .select('*');
```

RLS самостоятельно ограничивает набор доступных объектов.

### 6.2. Создание объекта

Доступно менеджеру.

```ts
const { data, error } = await supabase
  .from('objects')
  .insert({
    name,
    address,
  })
  .select()
  .single();
```

### 6.3. Редактирование объекта

Доступно менеджеру.

```ts
const { data, error } = await supabase
  .from('objects')
  .update({
    name,
    address,
  })
  .eq('id', objectId)
  .select()
  .single();
```

### 6.4. Удаление объекта

Доступно менеджеру.

```ts
const { error } = await supabase
  .from('objects')
  .delete()
  .eq('id', objectId);
```

Учитывать ограничения внешнего ключа: объект, на который ссылаются задачи, нельзя удалить без предварительного разрешения зависимости.

## 7. Работа с задачами

### 7.1. Получение списка задач

Таблица: `public.tasks`.

```ts
const { data, error } = await supabase
  .from('tasks')
  .select(`
    *,
    objects (
      id,
      name,
      address
    )
  `);
```

RLS определяет, какие задачи доступны текущему пользователю.

### 7.2. Получение задачи

```ts
const { data, error } = await supabase
  .from('tasks')
  .select(`
    *,
    objects (
      id,
      name,
      address
    )
  `)
  .eq('id', taskId)
  .single();
```

### 7.3. Создание задачи

Доступно менеджеру.

Обязательные данные:
- название;
- описание (может быть пустым);
- объект;
- исполнитель.

При создании:
- `status` устанавливается в `new`;
- `author_id` устанавливается равным ID текущего пользователя;
- `created_at` устанавливается БД.

```ts
const { data, error } = await supabase
  .from('tasks')
  .insert({
    title,
    description,
    object_id: objectId,
    assignee_id: assigneeId,
    author_id: userId,
    status: 'new',
  })
  .select()
  .single();
```

Начальная запись истории `NULL → new` создаётся триггером БД.

### 7.4. Редактирование задачи

Доступно менеджеру.

Менеджер может изменять поля задачи, кроме идентификатора и даты создания.

```ts
const { data, error } = await supabase
  .from('tasks')
  .update({
    title,
    description,
    object_id: objectId,
    assignee_id: assigneeId,
  })
  .eq('id', taskId)
  .select()
  .single();
```

Изменение статуса через обычный `UPDATE` не допускается.

### 7.5. Удаление задачи

Доступно менеджеру.

```ts
const { error } = await supabase
  .from('tasks')
  .delete()
  .eq('id', taskId);
```

Учитывать наличие связанных записей истории и ограничения внешнего ключа.

## 8. Изменение статусов задач

### 8.1. Общий принцип

Все изменения статуса выполняются через RPC-функцию:

`public.change_task_status(p_task_id, p_new_status, p_comment)`.

Пример вызова:

```ts
const { error } = await supabase.rpc(
  'change_task_status',
  {
    p_task_id: taskId,
    p_new_status: newStatus,
    p_comment: comment ?? null,
  }
);
```

Не выполнять изменение `tasks.status` через `.update()`.

### 8.2. Допустимые переходы

| Текущий статус | Новый статус | Кто выполняет |
|---|---|---|
| new | in_progress | Исполнитель |
| in_progress | review | Исполнитель |
| review | accepted | Менеджер |
| review | revision | Менеджер |
| revision | in_progress | Исполнитель |

Другие переходы запрещены на стороне БД.

### 8.3. Возврат на доработку

При переходе `review → revision` менеджер обязан указать комментарий.

Фронтенд должен:
- предоставить поле для комментария;
- не отправлять пустой комментарий;
- передавать комментарий в `p_comment`.

БД дополнительно проверяет наличие комментария. Клиентская валидация не заменяет серверную.

### 8.4. Обработка результата

При успешном вызове:
- обновить данные задачи;
- обновить историю изменений.

При ошибке:
- сохранить текущие данные интерфейса;
- показать сообщение об ошибке;
- не отображать переход как успешно выполненный.

## 9. История изменений

Таблица: `public.task_status_history`.

Получение истории конкретной задачи:

```ts
const { data, error } = await supabase
  .from('task_status_history')
  .select('*')
  .eq('task_id', taskId)
  .order('created_at', { ascending: true });
```

История должна отображать:
- предыдущий статус;
- новый статус;
- автора изменения;
- дату и время;
- комментарий, если он есть.

Для отображения имени пользователя при необходимости получать данные из `profiles`.

Фронтенд не должен:
- создавать записи истории вручную;
- редактировать записи истории;
- удалять записи истории.

Для `authenticated` на уровне прав таблицы разрешён только `SELECT`.

## 10. Рекомендуемая структура API-модулей

Разделить обращения к Supabase по сущностям:

```text
src/
  shared/
    api/
      supabase.ts
  entities/
    profile/
      api/
        profile.api.ts
    object/
      api/
        object.api.ts
    task/
      api/
        task.api.ts
        task-history.api.ts
```

Ответственность модулей:

- `profile.api.ts` — получение профиля пользователя.
- `object.api.ts` — получение, создание, редактирование и удаление объектов.
- `task.api.ts` — получение, создание, редактирование и удаление задач, вызов RPC для смены статуса.
- `task-history.api.ts` — получение истории задачи.

Компоненты интерфейса не должны содержать SQL-подобную логику работы с Supabase. Запросы следует вызывать через соответствующие API-модули.

## 11. Обработка ошибок и состояний запросов

Для всех операций с БД предусмотреть:

- состояние загрузки;
- состояние успешного получения данных;
- состояние пустого результата;
- состояние ошибки;
- состояние выполнения мутации.

Ошибки Supabase необходимо обрабатывать и преобразовывать в понятные пользователю сообщения.

Учитывать, что:
- RLS может вернуть пустой результат при отсутствии доступа к строкам;
- операции изменения могут завершиться ошибкой из-за ограничений RLS;
- RPC может вернуть ошибку при недопустимом переходе статуса;
- комментарий при возврате на доработку обязателен;
- удаление объекта или задачи может быть ограничено внешними ключами.

Не показывать пользователю технические детали и чувствительные данные из ответа сервера.

## 12. Требования безопасности

1. Использовать только публичный Supabase Anon Key на клиенте.
2. Не использовать Service Role Key во фронтенде.
3. Не хранить пароли и токены в исходном коде.
4. Не реализовывать собственную клиентскую систему разграничения доступа вместо RLS.
5. Не предоставлять фронтенду возможность напрямую изменять историю статусов.
6. Не изменять статус задачи через обычный UPDATE.
7. Не считать скрытие элементов интерфейса достаточной защитой операций.
8. Все операции должны выполняться в контексте текущей Auth-сессии.

## 13. Проверки интеграции

До завершения интеграции необходимо проверить работу через реальный Supabase API под тестовыми пользователями.

Тестовые аккаунты:
- `manager@test.com`;
- `executor1@test.com`;
- `executor2@test.com`.

Ожидаемая видимость данных:

| Таблица | Менеджер | Исполнитель 1 | Исполнитель 2 |
|---|---:|---:|---:|
| profiles | 3 | 1 | 1 |
| objects | 2 | 1 | 1 |
| tasks | 3 | 2 | 1 |
| task_status_history | 3 | 2 | 1 |

Дополнительные проверки:
- исполнитель не может получить чужую задачу;
- исполнитель не может изменить чужую задачу;
- исполнитель не может изменить поля задачи, кроме статуса;
- исполнитель не может создать задачу;
- исполнитель не может изменить историю;
- менеджер может создавать и редактировать задачи;
- прямой UPDATE статуса без RPC отклоняется;
- RPC разрешает только допустимые переходы;
- возврат на доработку без комментария отклоняется;
- история автоматически фиксирует создание задачи и смену статуса.

Проверки RLS через SQL Editor уже выполнялись с имитацией пользователя и показали ожидаемую видимость данных. Однако интеграционные проверки через реальный API ещё необходимо выполнить.

## 14. Критерии готовности интеграции

Интеграция фронтенда с Supabase считается готовой, когда:

- [ ] Supabase Client инициализируется через переменные окружения.
- [ ] Пользователь может авторизоваться и выйти из системы.
- [ ] После авторизации загружается его профиль и роль.
- [ ] Данные объектов загружаются с учётом RLS.
- [ ] Данные задач загружаются с учётом RLS.
- [ ] Менеджер может выполнять CRUD объектов и задач.
- [ ] Исполнитель видит только назначенные ему задачи и связанные объекты.
- [ ] Исполнитель может выполнять разрешённые переходы статусов.
- [ ] Менеджер может принимать задачи и возвращать их на доработку.
- [ ] При возврате на доработку комментарий обязателен.
- [ ] История изменений отображается и обновляется после операций.
- [ ] История не изменяется напрямую из фронтенда.
- [ ] Ошибки БД корректно обрабатываются интерфейсом.
- [ ] Проверки разграничения доступа пройдены через реальный Supabase API.
