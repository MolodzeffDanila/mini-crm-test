# Прораб — мини-CRM объектов и задач

Проект на React, TypeScript, Vite, Mantine UI и Supabase. Интерфейс на русском, открытая регистрация не используется.

## Демо

Приложение развёрнуто и доступно по ссылке: https://mini-crm-test-ruby.vercel.app/

## Структура

```text
src/
  app/          приложение и глобальные стили
  components/   общие UI-компоненты (TaskCard, TaskForm, ObjectForm и др.)
  features/     модули предметных областей (auth, objects, tasks, workspace)
  entities/     API-модули Supabase по сущностям (object, task, task-history)
  lib/          клиент Supabase
  types/        общие типы и модели
  main.tsx      точка входа и провайдеры
supabase/
  migrations/   версии схемы базы данных
  seed.sql      демонстрационные объекты и задачи
docs/
  AGENTS.md     техническая спецификация проекта
  CONTRACT.md   контракт взаимодействия Frontend ↔ Supabase
  DB-API.md     подключение фронтенда к БД и проверки интеграции
  demo-guide.md план демонстрации на созвоне
```

## Приложение

Деплой выполнен на Vercel: https://mini-crm-test-ruby.vercel.app/ (переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` заданы в настройках проекта). Локальный запуск — по инструкции ниже.

## Локальный запуск

1. Установите Node.js 20.19+ или 22.12+.
2. В корне проекта выполните `npm install`.
3. Создайте проект Supabase и примените миграции из `supabase/migrations` по порядку (SQL Editor или `supabase db push`). Вторая миграция переводит схему на контракт `objects`/`object_id`, роли `manager`/`executor`, статус `revision`, RPC `change_task_status` и защищённую историю. Третья приводит схему к финальному виду контракта: убирает служебные столбцы вне контракта и устанавливает канонические триггеры жизненного цикла.
4. В Supabase отключите публичную регистрацию: Authentication → Sign In / Providers → Email → отключить «Allow new users to sign up».
5. Создайте аккаунты вручную через Authentication → Users. Добавьте профиль каждому пользователю в SQL Editor, используя UUID из Auth:

   ```sql
   insert into public.profiles (id, role)
   values ('UUID_ИЗ_AUTH', 'manager'); -- либо executor
   ```

   После создания трёх аккаунтов демонстрационные объекты и задачи наполняются скриптом `supabase/seed.sql` (выполнить один раз в SQL Editor).

6. Скопируйте `.env.example` в `.env.local` и задайте `VITE_SUPABASE_URL` и публичный `VITE_SUPABASE_ANON_KEY` (Settings → API).
7. Запустите `npm run dev` — приложение откроется на `http://localhost:5173`. Production-сборка: `npm run build`, локальный просмотр сборки: `npm run preview`.

Публичный anon/publishable key рассчитан на клиент и ограничен RLS. Ключ `service_role` запрещено добавлять в клиентский `.env` или Git.

## Тестовые аккаунты

| Логин | Пароль | Роль |
|---|---|---|
| `manager@test.com` | `manager` | Постановщик |
| `executor1@test.com` | `executor` | Исполнитель |
| `executor2@test.com` | `executor` | Исполнитель |

Пароли задаются при создании пользователей вручную в Supabase (см. шаг 5 инструкции по запуску). Если аккаунт уже создан с другим паролем, сбросьте его в Authentication → Users → Reset password. Постановщик видит все объекты и задачи, исполнитель — только назначенные ему задачи и связанные объекты.

## Модель доступа

RLS включён на таблицах профилей, объектов, задач и истории. Менеджер видит все объекты и задачи; исполнитель — назначенные ему задачи и связанные объекты. Переход статуса выполняется через RPC `change_task_status`, а триггер БД проверяет допустимость перехода и комментарий при возврате на доработку. Изменение статуса и запись истории выполняются одной транзакцией; клиенту запрещены прямые операции записи в историю.

## Кратко для руководителя

Система помогает руководителю распределять работы по строительным объектам и видеть, на каком этапе находится каждая задача. Руководитель создаёт объект, указывает исполнителя и описание работы. Исполнитель видит только свои задачи и связанные с ними объекты, берёт задачу в работу и отправляет её на проверку. Руководитель принимает выполненную работу либо возвращает её на доработку с комментарием. История сохраняет автора и время каждого перехода. Ограничения встроены в базу данных: интерфейс не может открыть исполнителю чужие задачи или выполнить запрещённый переход. Доступ выдаётся вручную, публичной регистрации нет.

## Решения и допущения

- В базе используются значения ролей и статусов из контракта: `manager`, `executor`, `new`, `in_progress`, `review`, `accepted`, `revision`.
- Статус меняется только через `change_task_status`; историю пишет PostgreSQL в той же транзакции, поэтому подделать автора или время записи через API нельзя.
- Удаление объекта с задачами отклоняется ограничением внешнего ключа (`on delete restrict`), чтобы не удалять связанные задачи незаметно.
- Контракт профиля содержит только `id` и `role`; в интерфейсе исполнитель отображается по ID профиля.
- Начальные миграции создавали служебные столбцы вне контракта (`profiles.display_name`, `tasks.updated_at` и др.); миграция `202611070001_converge_schema_to_contract` убирает их, чтобы схема на любом окружении совпадала с контрактом.
