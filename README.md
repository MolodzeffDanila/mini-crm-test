# Прораб — мини-CRM объектов и задач

Проект на React, TypeScript, Vite, Mantine UI и Supabase. Интерфейс на русском, открытая регистрация не используется.

## Демо

Приложение развёрнуто и доступно по ссылке: https://mini-crm-test-ruby.vercel.app/

## Структура

```text
src/
  app/          приложение и глобальные стили
  components/   общие UI-компоненты (TaskCard, TaskForm, ObjectForm и др.)
  features/     модули предметных областей (auth, objects, tasks, workspace)
  entities/     API-модули Supabase по сущностям (object, task, task-history)
  lib/          клиент Supabase
  types/        общие типы и модели
  main.tsx      точка входа и провайдеры
supabase/
  migrations/   версии схемы базы данных
  seed.sql      демонстрационные объекты и задачи
docs/
  AGENTS.md           техническая спецификация проекта
  CONTRACT.md         контракт взаимодействия Frontend ↔ Supabase
  DB-API.md           подключение фронтенда к БД и проверки интеграции
  database-setup.md   создание базы данных с нуля (миграции, пользователи, демо-данные)
```

## Кратко о проекте

**Что это.** Система помогает руководителю распределять работы по строительным объектам и видеть, на каком этапе находится каждая задача. Работа устроена так:

1. Руководитель создаёт объект (стройку) и ставит по нему задачи: название, описание, исполнитель.
2. Исполнитель видит свои задачи, берёт задачу в работу, а закончив — отправляет на проверку.
3. Руководитель смотрит результат и либо принимает задачу, либо возвращает на доработку. При возврате комментарий обязателен — исполнитель всегда знает, что именно не так.
4. Каждый переход сохраняется в истории: кто, когда и что изменил. История видна обеим сторонам.

**Как защищены данные.** Права проверяются не на экране, а в самом хранилище данных — это как сейф, а не охранник у двери: даже если кто-то попробует получить или изменить данные, минуя интерфейс (технически — прямым запросом к базе), система всё равно откажет. Это проверено специальными тестами.

**Что исполнитель не может сделать** (даже специально, даже напрямую):

- увидеть чужие задачи или объекты, где его задач нет;
- создать, изменить или удалить задачу или объект;
- изменить описание, исполнителя или другие данные задачи;
- пропустить этапы — например, отправить на проверку задачу, которую не начинал, или принять свою же работу;
- стереть или переписать историю: записи создаются автоматически, удалять и редактировать их нельзя никому, включая руководителя.

**Кто может войти.** Регистрации в системе нет — учётные записи создаёт и выдаёт руководитель вручную. Пароли хранятся в зашифрованном виде, секретные ключи доступа к хранилищу нигде в коде и в репозитории не лежат.

Если коротко: руководитель управляет всем и видит всё; исполнитель видит и трогает только своё; каждый шаг зафиксирован и не может быть скрыт или подделан.

## Локальный запуск

1. Установите Node.js 20.19+ или 22.12+.
2. В корне проекта выполните `npm install`.
3. Создайте проект Supabase и примените миграции из `supabase/migrations` по порядку. Полная пошаговая инструкция по развёртыванию базы — создание проекта, миграции, отключение регистрации, пользователи, профили, демо-данные — в [`docs/database-setup.md`](docs/database-setup.md).
4. В Supabase отключите публичную регистрацию: Authentication → Sign In / Providers → Email → отключить «Allow new users to sign up».
5. Создайте аккаунты вручную через Authentication → Users и добавьте профили в SQL Editor (см. `docs/database-setup.md`, шаги 3–5; демо-данные наполняются `supabase/seed.sql`).
6. Скопируйте `.env.example` в `.env.local` и задайте `VITE_SUPABASE_URL` и публичный `VITE_SUPABASE_ANON_KEY` (Settings → API).
7. Запустите `npm run dev` — приложение откроется на `http://localhost:5173`. Production-сборка: `npm run build`, локальный просмотр сборки: `npm run preview`.

Публичный anon/publishable key рассчитан на клиент и ограничен RLS. Ключ `service_role` запрещено добавлять в клиентский `.env` или Git.

## Тестовые аккаунты

| Логин | Пароль | Роль |
|---|---|---|
| `manager@test.com` | `manager` | Постановщик |
| `executor1@test.com` | `executor` | Исполнитель |
| `executor2@test.com` | `executor` | Исполнитель |

Пароли задаются при создании пользователей вручную в Supabase (см. `docs/database-setup.md`, шаг 3). Если аккаунт уже создан с другим паролем, сбросьте его в Authentication → Users → Reset password. Постановщик видит все объекты и задачи, исполнитель — только назначенные ему задачи и связанные объекты.

## Модель доступа

RLS включён на таблицах профилей, объектов, задач и истории. Менеджер видит все объекты и задачи; исполнитель — назначенные ему задачи и связанные объекты. Переход статуса выполняется через RPC `change_task_status`, а триггер БД проверяет допустимость перехода и комментарий при возврате на доработку. Изменение статуса и запись истории выполняются одной транзакцией; клиенту запрещены прямые операции записи в историю.


## Решения и допущения

- В базе используются значения ролей и статусов из контракта: `manager`, `executor`, `new`, `in_progress`, `review`, `accepted`, `revision`.
- Статус меняется только через `change_task_status`; историю пишет PostgreSQL в той же транзакции, поэтому подделать автора или время записи через API нельзя.
- Удаление объекта с задачами отклоняется ограничением внешнего ключа (`on delete restrict`), чтобы не удалять связанные задачи незаметно.
- Контракт профиля содержит `id`, `role` и `display_name`; в интерфейсе авторы, исполнители и записи истории отображаются по имени из `profiles.display_name` (при недоступности имени — fallback на id).
- Начальные миграции создавали служебные столбцы вне контракта (`tasks.updated_at` и др.); миграция `202611070001_converge_schema_to_contract` убирает их, чтобы схема на любом окружении совпадала с контрактом, а `202611070002_add_profiles_display_name` добавляет в профили отображаемое имя.
