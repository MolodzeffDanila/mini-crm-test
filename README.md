# Прораб — мини-CRM объектов и задач

Стартовый проект на React, TypeScript, Vite, Mantine UI и Supabase. Интерфейс на русском, открытая регистрация не используется.

## Структура

```text
src/
  app/          приложение и глобальные стили
  components/   общие UI-компоненты
  features/     модули предметных областей
  lib/          клиенты внешних сервисов (Supabase)
  types/        общие типы и модели
  main.tsx      точка входа и провайдеры
supabase/
  migrations/   версии схемы базы данных
```

## Запуск

1. Установите Node.js 20.19+ или 22.12+.
2. В этой папке запустите `npm install`.
3. Создайте проект Supabase и примените миграции `supabase/migrations` по порядку. Вторая миграция переводит схему на контракт `objects`/`object_id`, роли `manager`/`executor`, статус `revision`, RPC `change_task_status` и защищённую историю.
4. В Supabase отключите публичную регистрацию: Authentication → Providers → Email → Allow new users to sign up.
5. Создайте аккаунты вручную через Authentication → Users. Добавьте профиль каждому пользователю в SQL Editor, используя UUID Auth:

   ```sql
   insert into public.profiles (id, display_name, role)
   values ('UUID_ИЗ_AUTH', 'Имя', 'manager'); -- либо executor
   ```

После создания трёх аккаунтов и применения миграций тестовые объекты и задачи можно наполнить скриптом `supabase/seed.sql` (выполнить один раз в SQL Editor).

6. Скопируйте `.env.example` в `.env.local`, задайте `VITE_SUPABASE_URL` и публичный `VITE_SUPABASE_ANON_KEY`.
7. Запустите `npm run dev` для разработки. Перед сборкой можно отдельно запустить `npm run lint` и `npm run typecheck`; production-сборка выполняется командой `npm run build`, локальный просмотр — `npm run preview`.

Публичный anon/publishable key рассчитан на клиент и ограничен RLS. Ключ `service_role` запрещено добавлять в клиентский `.env` или Git.

## Модель доступа

RLS включён на таблицах профилей, объектов, задач и истории. Менеджер видит все объекты и задачи; исполнитель — назначенные ему задачи и связанные объекты. Переход статуса выполняется через RPC `change_task_status`, а триггер БД проверяет допустимость перехода и комментарий при возврате на доработку. Изменение задачи и запись истории выполняются одной транзакцией. Клиенту запрещены прямые операции записи в историю.

## Кратко для руководителя

Система помогает руководителю распределять работы по строительным объектам и видеть, на каком этапе находится каждая задача. Руководитель создаёт объект, указывает исполнителя и описание работы. Исполнитель видит только свои задачи и связанные с ними объекты, берёт задачу в работу и отправляет её на проверку. Руководитель принимает выполненную работу либо возвращает её на доработку с комментарием. История сохраняет автора и время каждого перехода. Ограничения встроены в базу данных: интерфейс не может открыть исполнителю чужие задачи или выполнить запрещённый переход. Доступ выдаётся вручную, публичной регистрации нет.

## Решения и допущения

- В базе применяются значения ролей и статусов из API-контракта: `manager`, `executor`, `new`, `in_progress`, `review`, `accepted`, `revision`.
- Статус меняется только через `change_task_status`; историю пишет PostgreSQL в транзакции с переходом.
- Удаление объекта с задачами отклоняется ограничением внешнего ключа, чтобы не удалять связанные задачи.
- Для исполнителей в выборе показывается ID профиля: контракт профилей не содержит имени или email.
- В исходной миграции есть `profiles.display_name`; новые frontend-запросы это поле не используют, поскольку контракт профиля содержит только ID и роль.

## Что ещё не подтверждено или не реализовано

- Миграции и RLS требуют применения и интеграционной проверки на целевом Supabase-проекте.
- Тестовые аккаунты, демонстрационные данные и пароли не предоставлены в репозитории.
- Вход под тестовыми учётными записями и проверки API под обеими ролями требуют действующих паролей.
- История и CRUD реализованы в приложении, но их работа с удалённой БД не подтверждена до применения миграций.
- Деплой исключён из текущего этапа.
