# Спецификация: контракт взаимодействия Frontend ↔ Supabase

## 1. Общая информация

**Проект:** Мини-CRM «Объекты и задачи».

**Назначение:** описать контракт взаимодействия frontend-приложения с Supabase для реализации авторизации, получения данных, управления объектами и задачами, изменения статусов и просмотра истории.

### Технологии

- React
- TypeScript
- Vite
- `@supabase/supabase-js` v2
- Supabase Auth
- PostgreSQL
- Row Level Security (RLS)

### Основные правила интеграции

1. Все запросы к БД выполняются через Supabase Client.
2. Авторизация выполняется через Supabase Auth.
3. Роль пользователя определяется по таблице `profiles`.
4. Frontend не является источником безопасности. Все ограничения доступа обеспечиваются RLS и PostgreSQL.
5. Изменение статуса задачи выполняется исключительно через RPC `change_task_status`.
6. История изменения статусов доступна только для чтения. Записи создаются автоматически на стороне БД.
7. `service_role` и `secret` ключи запрещено использовать во frontend.

## 2. Конфигурация Supabase

### Переменные окружения

Использовать:

- `VITE_SUPABASE_URL` — URL Supabase проекта.
- `VITE_SUPABASE_ANON_KEY` — публичный Publishable Key или legacy anon key.

### Supabase Client

Файл: `src/lib/supabase.ts`.

Экспортировать:
- `supabase` — экземпляр Supabase Client либо `null`, если конфигурация отсутствует.
- `isSupabaseConfigured` — признак наличия необходимых переменных окружения.

Клиент создаётся один раз и используется всеми API-модулями приложения.

## 3. Модель данных

### 3.1. profiles

Профили пользователей.

| Поле | Тип | Описание |
|---|---|---|
| id | UUID | ID пользователя, связь с auth.users |
| role | TEXT | Роль пользователя |

Допустимые роли:
- `manager`
- `executor`

Особенности:
- Профиль создаётся и настраивается вне frontend.
- Пользователь может читать собственный профиль.
- Manager может читать профили всех пользователей.
- Executor не может читать профили других пользователей.
- В таблице нет поля `display_name`.

### 3.2. objects

Объекты, на которых выполняются задачи.

| Поле | Тип | Обязательность |
|---|---|---|
| id | UUID | Генерируется БД |
| name | TEXT | Обязательно |
| address | TEXT | Обязательно |

Доступ:
- Manager: чтение, создание, изменение, удаление.
- Executor: чтение объектов, связанных с назначенными ему задачами.

### 3.3. tasks

Задачи, назначенные исполнителям.

| Поле | Тип | Обязательность |
|---|---|---|
| id | UUID | Генерируется БД |
| title | TEXT | Обязательно |
| description | TEXT | Необязательно |
| object_id | UUID | Обязательно |
| assignee_id | UUID | Обязательно |
| status | TEXT | Обязательно |
| author_id | UUID | Обязательно |
| created_at | TIMESTAMPTZ | Генерируется БД |

Допустимые статусы:
- `new`
- `in_progress`
- `review`
- `accepted`
- `revision`

Доступ:
- Manager: чтение всех задач, создание, изменение и удаление.
- Executor: чтение только назначенных ему задач; изменение только разрешённых полей назначенных ему задач.
- Executor не может менять исполнителя, автора, объект, название и описание задачи.

### 3.4. task_status_history

История изменения статусов.

| Поле | Тип | Описание |
|---|---|---|
| id | UUID | ID записи |
| task_id | UUID | ID задачи |
| changed_by | UUID | ID пользователя, изменившего статус |
| from_status | TEXT | Предыдущий статус, NULL при создании |
| to_status | TEXT | Новый статус |
| comment | TEXT | Комментарий |
| created_at | TIMESTAMPTZ | Время изменения |

Доступ:
- Manager: чтение всей истории.
- Executor: чтение истории только назначенных ему задач.
- Frontend не создаёт, не изменяет и не удаляет записи истории.
- История формируется автоматически триггерами PostgreSQL.

## 4. Авторизация

Модуль: `src/features/auth/api/auth.api.ts`.

### 4.1. Вход

Использовать:

`supabase.auth.signInWithPassword()`

Входные данные:
- `email: string`
- `password: string`

Результат:
- `session`
- `user`
- `error`

После успешной авторизации приложение должно:
1. Получить текущую сессию.
2. Получить профиль пользователя из `profiles`.
3. Определить роль.
4. Загрузить доступные пользователю объекты и задачи.
5. Отобразить интерфейс в соответствии с ролью.

### 4.2. Выход

Использовать:

`supabase.auth.signOut()`

После выхода:
- очистить пользовательские данные из состояния приложения;
- очистить профиль;
- очистить выбранный объект;
- вернуть пользователя на экран авторизации.

### 4.3. Восстановление сессии

При запуске приложения:
- вызвать `supabase.auth.getSession()`;
- подписаться на `supabase.auth.onAuthStateChange()`;
- синхронизировать состояние приложения с текущей сессией;
- отписываться от события при размонтировании компонента.

Не выполнять повторную авторизацию, если действующая сессия уже существует.

### 4.4. Регистрация

Публичная регистрация не реализуется.

Пользователи создаются вручную через Supabase Dashboard.

### 4.5. Получение профиля

Запрос:

`profiles.select('id, role').eq('id', userId).single()`

Профиль используется для определения роли и настройки интерфейса.

## 5. Контракт API объектов

Модуль: `src/entities/object/api/object.api.ts`.

### 5.1. Получение объектов

Метод: `getObjects()`

Запрос:

`objects.select('id, name, address')`

Поведение:
- Manager получает все объекты.
- Executor получает только объекты, доступные через RLS.

### 5.2. Создание объекта

Метод: `createObject(data)`

Входные данные:

```ts
type CreateObjectInput = {
  name: string;
  address: string;
};
```

Запрос:

`objects.insert(data).select().single()`

Доступ: только Manager.

### 5.3. Изменение объекта

Метод: `updateObject(id, data)`

Входные данные:

```ts
type UpdateObjectInput = {
  name?: string;
  address?: string;
};
```

Запрос:

`objects.update(data).eq('id', id).select().single()`

Доступ: только Manager.

### 5.4. Удаление объекта

Метод: `deleteObject(id)`

Запрос:

`objects.delete().eq('id', id)`

Доступ: только Manager.

При наличии связанных задач удаление может быть отклонено ограничением внешнего ключа PostgreSQL. Frontend должен корректно обработать ошибку.

## 6. Контракт API задач

Модуль: `src/entities/task/api/task.api.ts`.

### 6.1. Получение задач

Метод: `getTasks()`

Запрос:

`tasks.select('id, title, description, object_id, assignee_id, status, author_id, created_at')`

Поведение:
- Manager получает все задачи.
- Executor получает только назначенные ему задачи.
- Дополнительная фильтрация по роли может использоваться в интерфейсе, но не заменяет RLS.

### 6.2. Создание задачи

Метод: `createTask(data)`

Входные данные:

```ts
type CreateTaskInput = {
  title: string;
  description?: string | null;
  object_id: string;
  assignee_id: string;
};
```

При создании frontend передаёт:
- `title`
- `description`
- `object_id`
- `assignee_id`
- `author_id` — ID текущего пользователя.
- `status` — `new`.

`created_at` генерируется БД.

Запрос:

`tasks.insert(data).select().single()`

Доступ: только Manager.

После создания задачи PostgreSQL автоматически добавляет начальную запись в `task_status_history` с переходом `NULL → new`.

### 6.3. Изменение задачи

Метод: `updateTask(id, data)`

Входные данные для Manager:

```ts
type UpdateTaskInput = {
  title?: string;
  description?: string | null;
  object_id?: string;
  assignee_id?: string;
};
```

Менеджер может изменять данные задачи.

Executor не использует этот метод для изменения содержимого задачи.

Изменение статуса через `updateTask` запрещено.

### 6.4. Удаление задачи

Метод: `deleteTask(id)`

Запрос:

`tasks.delete().eq('id', id)`

Доступ: только Manager.

## 7. Контракт изменения статусов

Изменение статуса выполняется через PostgreSQL RPC.

Функция:

`change_task_status(p_task_id, p_new_status, p_comment)`

Метод frontend:

`changeTaskStatus(taskId, newStatus, comment?)`

Пример:

```ts
await supabase.rpc('change_task_status', {
  p_task_id: taskId,
  p_new_status: newStatus,
  p_comment: comment ?? null,
});
```

### 7.1. Разрешённые переходы

| Текущий статус | Новый статус | Кто выполняет |
|---|---|---|
| new | in_progress | Executor |
| in_progress | review | Executor |
| review | accepted | Manager |
| review | revision | Manager |
| revision | in_progress | Executor |

Все остальные переходы запрещены.

### 7.2. Комментарий при возврате на доработку

При переходе `review → revision`:
- Manager обязан указать комментарий.
- Frontend должен запросить комментарий перед отправкой.
- Пустой комментарий не отправляется.
- PostgreSQL дополнительно проверяет обязательность комментария.

### 7.3. Поведение после перехода

После успешного вызова RPC:
1. Обновить данные задачи.
2. Обновить отображаемый статус.
3. Обновить историю задачи, если она открыта.

При ошибке:
- не менять локальный статус;
- показать сообщение об ошибке;
- сохранить актуальное состояние задачи.

Запрещено выполнять:

`supabase.from('tasks').update({ status: newStatus })`

## 8. Контракт API истории

Модуль: `src/entities/task-history/api/task-history.api.ts`.

### Получение истории задачи

Метод: `getTaskHistory(taskId)`

Запрос:

`task_status_history.select('*').eq('task_id', taskId).order('created_at', { ascending: true })`

Возвращаемые данные:

```ts
type TaskStatusHistory = {
  id: string;
  task_id: string;
  changed_by: string;
  from_status: TaskStatus | null;
  to_status: TaskStatus;
  comment: string | null;
  created_at: string;
};
```

Доступ:
- Manager может получить историю любой задачи.
- Executor может получить историю только назначенной ему задачи.

Операции создания, изменения и удаления истории на frontend отсутствуют.

## 9. TypeScript-типы

Рекомендуется централизованно определить типы.

```ts
export type Role = 'manager' | 'executor';

export type TaskStatus =
  | 'new'
  | 'in_progress'
  | 'review'
  | 'accepted'
  | 'revision';

export interface Profile {
  id: string;
  role: Role;
}

export interface ObjectEntity {
  id: string;
  name: string;
  address: string;
}

export interface Task {
  id: string;
  title: string;
  description: string | null;
  object_id: string;
  assignee_id: string;
  status: TaskStatus;
  author_id: string;
  created_at: string;
}

export interface TaskStatusHistory {
  id: string;
  task_id: string;
  changed_by: string;
  from_status: TaskStatus | null;
  to_status: TaskStatus;
  comment: string | null;
  created_at: string;
}
```

Типы должны соответствовать реальной схеме PostgreSQL.

Не использовать `site_id`, `rework`, `transition_task` и `display_name` в контрактах БД.

## 10. Обработка ошибок

Все API-модули должны возвращать результат запроса и обрабатывать ошибки Supabase.

Основные ситуации:

| Ситуация | Поведение frontend |
|---|---|
| Неверный email или пароль | Сообщение об ошибке авторизации |
| Нет сессии | Показать экран входа |
| Профиль не найден | Показать ошибку загрузки профиля |
| Недостаточно прав | Показать сообщение об отсутствии доступа |
| Недопустимый переход статуса | Показать ошибку изменения статуса |
| Нет обязательного комментария | Не отправлять запрос |
| Ошибка загрузки объектов | Показать ошибку загрузки |
| Ошибка загрузки задач | Показать ошибку загрузки |
| Ошибка загрузки истории | Показать ошибку загрузки истории |

Технические подробности ошибок можно выводить через `console.error` в процессе разработки. Пользователю показывать понятные сообщения без SQL-текста и внутренних деталей БД.

## 11. Ролевая логика frontend

### Manager

Доступные операции:
- просмотр всех объектов;
- создание, редактирование и удаление объектов;
- просмотр всех задач;
- создание, редактирование и удаление задач;
- назначение исполнителей;
- принятие задачи после проверки;
- возврат задачи на доработку с комментарием;
- просмотр истории задач.

### Executor

Доступные операции:
- просмотр назначенных ему задач;
- просмотр связанных с ними объектов;
- перевод задачи из `new` в `in_progress`;
- отправка задачи на проверку (`review`);
- повторный запуск задачи после возврата на доработку (`revision → in_progress`);
- просмотр истории назначенных ему задач.

Frontend скрывает недоступные действия в зависимости от роли.

При этом окончательное решение о доступе всегда принимает PostgreSQL через RLS и триггеры.

## 12. Фактическая структура API

Реализация использует следующую раскладку (допускается адаптация без изменения контрактов взаимодействия с БД):

```text
src/
  lib/
    supabase.ts               единый Supabase Client (isSupabaseConfigured, supabase)

  entities/
    object/
      api/
        object.api.ts         CRUD объектов
    task/
      api/
        task.api.ts           CRUD задач + RPC change_task_status
        task-history.api.ts   чтение истории задачи

  features/
    auth/
      useAuth.ts              сессия, профиль, роль, вход/выход

  types/
    domain.ts                 Role, TaskStatus, Task, TaskStatusHistory и подписи статусов
```

Клиент создаётся в `src/lib/supabase.ts`; модуль `src/shared/api/supabase.ts` из ранних версий спецификации удалён как дублирующий.

## 13. Критерии готовности интеграции

Интеграция frontend с Supabase считается готовой, когда:

1. Пользователь может войти под существующей учётной записью.
2. После перезагрузки страницы восстанавливается сессия.
3. Пользователь может выйти из системы.
4. Роль пользователя корректно определяется по `profiles`.
5. Manager получает все объекты и задачи.
6. Executor получает только назначенные ему задачи и связанные объекты.
7. Manager может выполнять CRUD объектов и задач.
8. Executor может выполнять только разрешённые действия с задачами.
9. Все разрешённые переходы статусов работают через RPC.
10. Недопустимые переходы отклоняются.
11. Возврат на доработку требует комментария.
12. История автоматически отображает изменения статусов.
13. Executor не может получить данные чужих задач через прямой API-запрос.
14. Frontend не содержит секретных ключей Supabase.

## 14. Ограничения реализации

- Не изменять существующую схему БД ради удобства frontend.
- Не добавлять поля, которых нет в БД.
- Не создавать дополнительные RPC без необходимости.
- Не переносить проверки безопасности исключительно на frontend.
- Не записывать историю статусов самостоятельно.
- Не менять статусы задач прямыми UPDATE-запросами.
- Не использовать `service_role` в браузере.
- Не реализовывать публичную регистрацию пользователей.

Главный принцип: frontend реализует интерфейс и вызывает предусмотренные операции Supabase, а PostgreSQL остаётся источником истины для данных, бизнес-ограничений и прав доступа.
