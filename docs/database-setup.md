# Создание базы данных с нуля

Полная инструкция по развёртыванию базы данных мини-CRM в новом проекте Supabase. Занимает 15–20 минут, подходит бесплатный тариф.

## Шаг 0. Создайте проект Supabase

1. Зайдите на https://supabase.com/dashboard → **New project**.
2. Укажите имя, пароль базы данных (сохраните его) и регион.
3. Дождитесь окончания provisioning (1–2 минуты).

## Шаг 1. Примените миграции

Откройте **SQL Editor** → **New query** и по очереди выполните файлы из `supabase/migrations` в порядке имен:

| Файл | Что создаёт |
|---|---|
| `202611060001_initial_schema.sql` | Таблицы `profiles`, `sites`, `tasks`, `task_history`, enum-типы, первые триггеры и политики RLS |
| `202611060002_align_db_api_contract.sql` | Переименование в контрактные `objects`/`object_id`/`task_status_history`, роли `manager`/`executor`, статус `revision`, RPC `change_task_status`, канонические политики RLS |
| `202611070001_converge_schema_to_contract.sql` | Финальный вид схемы по контракту: убирает служебные столбцы, переустанавливает канонические триггеры жизненного цикла |
| `202611070002_add_profiles_display_name.sql` | Столбец `profiles.display_name` для отображения имён в интерфейсе |

Каждый файл — целиком в один запрос, затем **Run**. Все четыре миграции идемпотентны в пределах одной схемы: если часть из них уже применялась (например, база собиралась вручную), повторный прогон безопасен.

Итоговая схема:

- `profiles(id, role, display_name)` — профили и роли пользователей;
- `objects(id, name, address)` — строительные объекты;
- `tasks(id, title, description, object_id, assignee_id, status, author_id, created_at)` — задачи;
- `task_status_history(id, task_id, changed_by, from_status, to_status, comment, created_at)` — неизменяемая история переходов;
- RPC `change_task_status(task_id, new_status, comment)` — единственный способ сменить статус.

## Шаг 2. Отключите открытую регистрацию

**Authentication** → **Sign In / Providers** → **Email** → снимите галочку **Allow new users to sign up** → Save.

## Шаг 3. Создайте пользователей

**Authentication** → **Users** → **Add user** → **Create new user**. Создайте трёх пользователей:

| Email | Пароль | Роль |
|---|---|---|
| `manager@test.com` | `manager` | Постановщик |
| `executor1@test.com` | `executor` | Исполнитель |
| `executor2@test.com` | `executor` | Исполнитель |

Пароль задаётся при создании. Если пользователь уже существует с другим паролем — **Reset password** в меню пользователя.

## Шаг 4. Создайте профили

У каждого пользователя скопируйте UUID (колонка `id` в списке Users) и выполните в SQL Editor:

```sql
insert into public.profiles (id, role, display_name) values
  ('UUID_МЕНЕДЖЕРА', 'manager', 'Менеджер'),
  ('UUID_ИСПОЛНИТЕЛЯ_1', 'executor', 'Исполнитель 1'),
  ('UUID_ИСПОЛНИТЕЛЯ_2', 'executor', 'Исполнитель 2');
```

Профиль обязателен: без строки в `profiles` вход в приложение будет отклонён с ошибкой «Не удалось определить роль».

## Шаг 5. Наполните демонстрационные данные

Выполните в SQL Editor один раз файл `supabase/seed.sql`. Он:

- находит UUID трёх аккаунтов по email;
- создаёт 2 объекта и 3 задачи;
- прогоняет задачи через реальные переходы статусов от имени исполнителей и менеджера, чтобы история выглядела естественно (создание, работа, проверка, принятие, возврат на доработку с комментарием);
- заполняет `display_name` демо-аккаунтов.

Повторный запуск дублирует объекты и задачи — файл рассчитан на однократное выполнение (idempotentен только блок с именами).

## Шаг 6. Получите ключи для приложения

**Project Settings** → **API**:

- `Project URL` → переменная `VITE_SUPABASE_URL`;
- `anon public` (или `publishable`) ключ → переменная `VITE_SUPABASE_ANON_KEY`.

Скопируйте `.env.example` в `.env.local` и подставьте значения. Ключ `service_role` никуда не копируйте — он обходит RLS и должен оставаться только в dashboard.

## Шаг 7. Проверка

1. `npm install && npm run dev`, откройте `http://localhost:5173`.
2. Войдите как `manager@test.com` — должны быть видны оба объекта и все задачи с историей.
3. Выйдите, войдите как `executor1@test.com` — только «Мои задачи» и объект, связанный с ними.
4. Возьмите задачу в работу и отправьте на проверку; вернитесь под менеджером и примите её или верните на доработку с комментарием — каждый переход появится в истории.

Готовые сценарии проверки ограничений доступа (включая прямые запросы к API в обход интерфейса) перечислены в [`DB-API.md`](DB-API.md), раздел 13.
