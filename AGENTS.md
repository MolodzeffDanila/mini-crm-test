# Мини-CRM «Объекты и задачи» — техническая спецификация

## 1. Назначение системы

Разработать небольшую CRM для строительной компании, в которой руководители создают объекты (стройки), ставят по ним задачи исполнителям, а исполнители выполняют задачи и отправляют их на проверку.

## 2. Технологический стек

- Frontend: React + TypeScript.
- Backend / Database / Authentication: Supabase.
- UI-библиотека: на выбор разработчика.
- Размещение: Vercel, Netlify или собственный сервер.

## 3. Роли пользователей

В системе предусмотрены две роли.

### 3.1. Постановщик

Возможности:

- Просматривать все объекты и задачи.
- Создавать, редактировать и удалять объекты.
- Создавать, редактировать и удалять задачи.
- Назначать исполнителей на задачи.
- Принимать задачи.
- Возвращать задачи на доработку.
- Просматривать историю изменений задач.

### 3.2. Исполнитель

Возможности:

- Просматривать только свои задачи.
- Просматривать только объекты, в которых у него есть задачи.
- Переводить назначенные ему задачи в статус «В работе».
- Отправлять задачи на проверку.
- Просматривать историю изменений задач.

Постановщиков и исполнителей может быть несколько.

## 4. Сущности и их поля

### 4.1. Объект

Объект представляет собой строительную площадку.

Поля:

- Название.
- Адрес.

В карточке объекта отображается список связанных задач с их текущими статусами.

### 4.2. Задача

Поля:

- Название.
- Описание.
- Объект.
- Исполнитель.
- Статус.
- Автор.
- Дата создания.

### 4.3. История задачи

Для каждой смены статуса необходимо сохранять:

- Кто изменил статус.
- Когда произошло изменение.
- Из какого статуса.
- В какой статус.
- Комментарий (если есть).

История доступна для просмотра обеим ролям.

## 5. Жизненный цикл задачи

### 5.1. Статусы

1. Новая.
2. В работе.
3. На проверке.
4. Принята.
5. На доработке.

### 5.2. Разрешённые переходы

| Исходный статус | Новый статус | Кто выполняет |
|---|---|---|
| Создание задачи | Новая | Постановщик |
| Новая | В работе | Назначенный исполнитель |
| В работе | На проверке | Назначенный исполнитель |
| На проверке | Принята | Постановщик |
| На проверке | На доработке | Постановщик |
| На доработке | В работе | Назначенный исполнитель |

При переводе задачи в статус «На доработке» постановщик обязан указать комментарий.

Другие переходы между статусами запрещены.

## 6. Экраны приложения

### 6.1. Авторизация

- Вход по email и паролю.
- Открытая регистрация отключена.

### 6.2. Список объектов

- Отображение объектов.
- Для постановщика отображаются все объекты.
- Для исполнителя отображаются только объекты, в которых у него есть задачи.

### 6.3. Карточка объекта

- Отображение названия и адреса объекта.
- Список задач объекта.
- Отображение статусов задач.

### 6.4. Карточка задачи

- Отображение всех полей задачи.
- Кнопки доступных действий в зависимости от роли и текущего статуса.
- История изменения статусов.

### 6.5. Мои задачи

- Экран для исполнителя.
- Отображение только задач текущего исполнителя.

Интерфейс должен показывать только те действия, которые доступны текущему пользователю в текущем статусе задачи.

## 7. Требования к безопасности

Безопасность должна обеспечиваться на уровне базы данных Supabase, а не только на уровне интерфейса.

Обязательные требования:

1. Настроить Row Level Security (RLS) для ограничения доступа к данным.
2. Исполнитель не может читать или изменять чужие задачи.
3. Исполнитель может видеть только свои задачи и связанные с ними объекты.
4. Переходы между статусами проверяются на стороне базы данных.
5. Запрещённый переход статуса не должен выполняться даже при прямом обращении к Supabase API.
6. Историю изменения статусов нельзя подделать, изменить или удалить через API.
7. Открытая регистрация пользователей отключена.
8. Тестовые пользователи создаются вручную в Supabase.
9. Секретные ключи (service_role и аналогичные) не должны попадать во frontend и Git-репозиторий.

## 8. Критерии готовности

- Пользователь может войти по email и паролю.
- Постановщик может создавать и управлять объектами и задачами.
- Исполнитель видит только назначенные ему задачи и связанные объекты.
- Исполнитель может взять новую задачу в работу.
- Исполнитель может отправить задачу на проверку.
- Постановщик может принять задачу или вернуть её на доработку с обязательным комментарием.
- Исполнитель может повторно взять задачу на доработке в работу.
- Все изменения статусов сохраняются в истории.
- История доступна обеим ролям и защищена от подделки и удаления.
- Запрещённые переходы статусов блокируются базой данных.
- Ограничения доступа работают при прямом обращении к Supabase API, а не только через UI.

## 9. Результат разработки

Необходимо предоставить:

1. Рабочее приложение с доступом к нему.
2. Доступы минимум к одному постановщику и двум исполнителям.
3. Базу данных с 2–3 объектами и несколькими задачами в разных статусах.
4. GitHub-репозиторий с миграциями базы данных.
5. README с инструкцией по запуску проекта.
6. Видео продолжительностью до 5 минут или текст объёмом около половины страницы для руководителя без технического образования. Объяснить устройство системы, защиту данных и ограничения исполнителя.
7. Список самостоятельно принятых решений и допущений, а также того, что не удалось реализовать.

После сдачи необходимо продемонстрировать результат на созвоне продолжительностью 30–40 минут.

## 11. Предлагаемый порядок выполнения

Это порядок реализации задач, а не дополнительные требования к продукту.

| Этап | Содержание | Результат |
|---|---|---|
| 1 | Подготовка проекта | Работающий React-проект |
| 2 | Supabase и схема БД | Созданная структура данных |
| 3 | RLS и бизнес-логика | Защищённая база и переходы статусов |
| 4 | Авторизация | Вход пользователей с определением роли |
| 5 | Объекты | CRUD объектов и карточка объекта |
| 6 | Задачи | CRUD задач и назначение исполнителей |
| 7 | Жизненный цикл | Изменение статусов и история |
| 8 | Интерфейсы ролей | Списки объектов, задач и «Мои задачи» |
| 9 | Тестирование | Проверенные сценарии и ограничения доступа |
| 10 | Развёртывание и сдача | Готовое приложение и документация |

**Важный технический момент:** этап 3 нельзя откладывать до конца разработки. Проверку переходов статусов и защиту истории нужно реализовать непосредственно в PostgreSQL (например, через функции и триггеры), а RLS настроить до подключения основных пользовательских сценариев. Иначе можно получить приложение, в котором интерфейс работает правильно, но бизнес-ограничения обходятся прямыми запросами к Supabase API.
